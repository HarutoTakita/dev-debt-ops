コードベースの理解度を実測・促進する開発プラットフォーム

クイズで理解度を実測し、理解度マップで可視化。
低品質コードを AI の自動修正 PRで改善。

AI エージェントがサブエージェント・MCP・Hookを活用してリポジトリを多角的に解析。
機能の抽出から理解度の実測、コード品質の検知、修正提案までを一気通貫で
自動化します。

AIエージェント × MCP で高度なリポジトリ探索 GitHub 連携でかんたんログイン PII・シークレットを自動マスキング モバイル対応 スケーラブルな Cloud Run 構成

課題は「コード」だけじゃない

動くが誰も中身を理解していないコードは、コード品質の問題とは別の理解ギャップ。 変更速度・レビュー品質・オンボーディングを静かに蝕みます。

01

書いた人しか分からない

担当者の異動・退職でコードが事実上ブラックボックスに。レビューも改修も止まる。

02

AI 生成コードの増殖

生成量が増えるほど、誰にも理解されないまま本番へ。レビューが追いつかない。

03

優先順位がつかない

品質の低いコードは山積みでも「どこから手をつけるか」が主観頼み。緊急度を測れない。

理解度とコード品質を、可視化して改善する

理解度

  • 可視化｜理解度マップ — 誰がどこを理解しているかをファイル単位のグラフで俯瞰。
  • 改善｜クイズと学習 — クイズで実測し、学習プランで埋める。合格で理解度↑。

コード品質

  • 可視化｜コード品質マップ — ファイル単位で品質の低いコードの分布を俯瞰。
  • 改善｜コード改善 — AI に頼む（修正 PR）／人に頼む（Issue）で対応。

実測 → 改善の閉ループ

検知は出発点ではなく「どの理解ギャップが緊急か」を示すホットスポット信号。主役は理解度の実測と向上です。

  1. 01

    解析する

    検知・理解度・機能クラスタリングをまとめて実行。

  2. 02

    クイズで実測

    git blame に頼らず、理解度を能動的に計測する。

  3. 03

    学習で深める

    チーム資産を優先した学習プランで理解度を引き上げる。

  4. 04

    修正 PR

    AI が改善案を生成し、GitHub に修正 PR を作成する。

FEATURES

アプリにできること

解析からダッシュボード、可視化、改善までを 1 つのワークスペースで。

Dashboard

ダッシュボード — 全体像を一目で

チームの理解度とコード品質を一枚で俯瞰。「学習を優先すべき領域」と推移を確認できます。閲覧専用に保ち、解析はトップバーから実行します。

  • ・チーム理解度のサマリ＋低品質ファイル
  • ・理解度 × コード品質の推移グラフ
  • ・優先対応リスト

Understanding Map

理解度マップ — 誰がどこを分かっているか

リポジトリをファイル単位のグラフで可視化。ノード＝ファイル、色＝理解度、線＝ファイル間の依存・呼び出し（import と関数コールを解析）。上部の機能フィルタで特定機能に関わるファイル群だけに絞り込め、マップ／リストの両ビューに効きます。

  • 理解済み
  • 部分理解
  • 未理解
  • 未着手

Code Quality Map

コード品質マップ — 品質の分布を俯瞰

ソースコードをファイル単位で閲覧し、どのファイルに品質の問題が多いかを俯瞰。重複・複雑度・dead code・AI 生成痕跡の検知結果を理解度と重ね、着手すべきホットスポットを見つけます。

Quizzes & Learning

クイズと学習 — 実測して理解を深める

「クイズ」で L1〜L5 の問題に答えて理解度を計測し、「学習」でプランを進めて理解度を引き上げます。git blame に頼らず能動的に計測するので、単独開発・コードを書かない PM でも計測できます。

  • ・このコードを理解する — リポジトリ特有の機能をコードウォークスルーで学ぶ
  • ・技術スタックを学ぶ — 関連技術の公式ドキュメント / チュートリアル
  • ・未学習 / 学習中 / 理解済み / 要復習 のステータス

Code Improvement

コード改善 — PR / Issue で返す

改善対象リストから対象を選ぶと、該当コードを行ハイライトで解説。「AI に頼む」で修正 PR を自動生成、「人に頼む」で担当者を割り当てた GitHub Issue を作成します。

INFRASTRUCTURE

インフラ構成

Google Cloud 上のコンテナ構成。重い解析は非同期ワーカーへ分離し、Webhook 駆動で自動スケールします。

利用者 → HTTPS LB ＋ Cloud Armor → api (Cloud Run) → Cloud Tasks → service (内部 Cloud Run)

アプリ実行 — Cloud Run

api（外部公開・SPA 同梱）と service（内部・重い解析の Cloud Tasks ターゲット）を分離。

データ — Cloud SQL

PostgreSQL ＋ pgvector。Alembic でスキーマ管理。

非同期ジョブ — Cloud Tasks

検知・理解度・クラスタリング等の重処理をワーカーへ委譲。冪等・再配送前提の設計。

公開・防御 — LB / Cloud Armor

外部 HTTPS ロードバランサ＋マネージド証明書。レート制限はエッジで強制。

機密・レジストリ

Secret Manager（平文環境変数は不可）／Artifact Registry でコンテナ管理。

IaC — Terraform

全リソースをコード化。この LP も api と同一ドメインの /lp に同梱して配信。

SECURITY

セキュリティでこだわっていること

認証・セッション

アクセス JWT（5 分）とリフレッシュ（7 日・DB 管理）の Cookie を分離。ローテーション＋再利用検出、`token_epoch` による即時ログアウト無効化。

CSRF / オリジン

SameSite=Lax ＋ Origin 検証ミドルウェア、トークンに固有 audience を付与して用途を分離。

鍵を持たない設計

Workload Identity Federation で長期クレデンシャルを排除。秘密は Secret Manager に集約（平文環境変数なし）。

ジョブ分離（方式 B）

キューには秘密を載せず、ワーカーが実行時に Secret Manager から GitHub トークンを mint。キュー無効時はフェイルクローズ。

エッジでのレート制限

Cloud Armor によりアプリ手前で制限。アプリ内のレート制御に依存しません。

LLM の安全策

リポジトリ内容は「データ（指示ではない）」として境界を明示。生成物を検証（空・巨大な改変を拒否）し、PR は未レビュー明示。

エージェント入力のマスキング

エージェント（LLM）に情報を与える際は、Cloud DLP（Sensitive Data Protection）と detect-secrets で PII・シークレットをマスキングしてから送信します。

脆弱性スキャン（OWASP 準拠）

OWASP に準拠した脆弱性スキャンを実施済み。認証・入力・依存関係など主要なリスク観点を点検しています。

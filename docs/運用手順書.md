# DevDebtOps 運用手順書（Runbook）

このリポジトリを初めて触る人が、**追加開発（拡張）／インフラ変更／CI・CD 変更／デプロイ／ドキュメント更新**を
一通り行えるようにするための実務手順書。各手順は実コード・実ワークフローに基づき、根拠となるファイルパスを併記する。

- プロダクトの思想・スタック概要: [`README.md`](../README.md)

- 画面の使い方（利用者向け）: [`docs/取扱説明書/README.md`](取扱説明書/README.md)

## 0. 全体像

- モノレポ構成:
  - `frontend/` — SvelteKit 2 SPA（Svelte 5 runes / shadcn-svelte / Tailwind v4 / bun）
  - `backend/` — uv workspace（`shared` 共有モデル / `api` FastAPI 外部公開 / `service` 重処理ワーカー）
  - `infra/` — Terraform（`gcp` 本体 / `bootstrap/gcp` WIF・state・deploy SA）
  - `docker/` — `api.Dockerfile` / `service.Dockerfile`（`dev` / `runtime` ステージ）
  - `landing/` — 静的 LP（アプリと同一ドメインの `/lp` で配信、6 言語対応）
  - `docs/` — ドキュメント（本書・reference・取扱説明書・infra・issue）
  - `.claude/skills/` — 作業補助スキル（commit / issue / pr / push / release-version）
- 実行構成: Cloud Run（api=外部LB / service=内部・Cloud Tasks ターゲット）+ Cloud SQL(PostgreSQL) + Secret Manager + Cloud Armor + Artifact Registry。認証は Cookie ベース（JWT access + DB-backed refresh）。

## 1. ローカル開発環境のセットアップ

```sh
cp .env.example .env.dev          # 初回のみ（docker compose が参照）
docker compose watch              # db + api(:8000) + service を起動（コード同期）
cd frontend && bun run dev        # Vite HMR :5173、/api を :8000 にプロキシ
```

- 補助: `docker compose --profile tools up`（pgAdmin :5050）/ `scripts/dev-up.sh`（起動＋全ログを `docs/logs/` に保存）。
- 本番相当ローカル: `docker compose -f compose.prod.yml up --build`（Traefik :8080、api 3 レプリカ + `migrate` ワンショット）。
- **デモデータ**（GitHub 不要でスクショ/動作確認）:
  ```sh
  echo "DEMO_MODE_ENABLED=true" >> .env.dev && docker compose watch
  docker compose exec api uv run --directory api python -m app.scripts.seed_demo   # 冪等（reset で入れ直し）
  ```
- dev の api コンテナは起動時にリトライ付きで `alembic upgrade head` を実行する（DB 空でも自動でスキーマ作成）。**本番/カナリアでは boot でマイグレーションしない**（§5 参照）。

## 2. 追加開発（拡張）の進め方

### 2.1 ブランチ / コミット / PR

- 既定の開発ブランチは **`develop`**（統合ブランチ）、安定ブランチは **`main`**。作業は `feature/*` か `develop` で行い、**PR は `develop` 宛**に出す（マージ後の `Closes #N` は手動 close 運用）。
- コミットメッセージ規約（`.claude/skills/commit`）: `<emoji> [<type>] <日本語説明>`。type は `feat`(:sparkles:) / `fix`(:bug:) / `update`(:zap:) / `docs`(:books:) / `chore`(:hammer:)。`/commit`・`/pr`・`/push` スキルが利用可。
- 品質ゲートは自動で走る（バイパス禁止・§2.5）。

### 2.2 フロントエンド（`frontend/`、bun）

| 目的 | コマンド |
|---|---|
| 開発サーバ | `bun run dev` |
| ビルド | `bun run build` → `frontend/build/` |
| 型チェック | `bun run check`（svelte-check、警告もエラー扱い） |
| リント | `bun run lint`（prettier --check + eslint） |
| 整形 | `bun run format` |
| 単体テスト | `bun run test:unit`（vitest。browser=chromium / node のデュアル） |
| 画面スクショ | `bun run screenshots`（§6・取扱説明書用） |

規約: 全ファイル kebab-case。**Svelte 5 runes のみ**（`$:`/`writable()` 不可）。`src/lib/components/ui/`（shadcn プリミティブ）は**編集禁止**——`ui/` 外のラッパで合成する。API レスポンスは `src/lib/api/schemas.ts` の Zod v4 で検証。詳細は `CLAUDE.md`「フロントエンド」節。

### 2.3 i18n（多言語）

- アプリ UI: Paraglide 2.0。`frontend/messages/{ja,en,zh,ko,es,de}.json`（全キー一致必須）+ `frontend/project.inlang/settings.json`（`locales`）。文言追加は全言語へ。`bun run check` が compile も走らせる。
- LP: `landing/i18n/`（`ja-source.json` + 各言語 json）→ `landing/i18n/build.py` で `landing/i18n.js` を再生成。翻訳追加時は §10 の LP 手順に従う。

### 2.4 バックエンド（`backend/`、uv workspace）

| 目的 | コマンド（`cd backend`） |
|---|---|
| 依存解決 | `uv sync --all-packages`（ロック更新は `uv lock`） |
| テスト | `uv run --directory api pytest`（`shared`/`service` も `--directory <member>`。api は Postgres の `test` DB 必要。ローカルは `DATABASE_URL=...localhost:5433/app`） |
| リント | `uv run ruff check shared/shared api/app service/service && uv run ruff format --check shared/shared api/app service/service` |
| 型チェック | `uv run ty check shared/shared api/app service/service` |

規約: 4 スペース / ダブルクォート / 120 桁。Python は snake_case。**更新系は PATCH**。**DB は api 所有**（Alembic・エンジンは `api`、`service` は共有 ORM に DML のみ）。`Annotated[T, Depends(f)]` の**パラメータ順序を変えない**（pytest teardown で DeadlockDetectedError）。`app.*` 名前空間は不変。詳細は `CLAUDE.md`「バックエンド」節。

### 2.5 品質ゲート（自動）

- ローカル: **lefthook**（インストール: `./frontend/node_modules/.bin/lefthook install`）。pre-commit=ruff check/format・prettier・eslint・gitleaks、pre-push=ty・svelte-check。**バイパスせず根本修正**する。
- CI: `.github/workflows/ci.yml`（push/PR to `develop`,`main`）が `check-backend`（ruff+ty）/ `test-backend`（pytest+Postgres）/ `lint-frontend`（prettier+eslint+svelte-check）/ `test-frontend`（vitest）を実行。
- 補足: gitleaks はローカル未導入だと pre-commit でスキップ表示になるが CI で強制される。

## 3. データベース / マイグレーション

- Alembic は **api が所有**（`backend/api/alembic.ini` / `backend/api/app/alembic/versions/`、`NNNN_<slug>.py` の線形チェーン）。接続は asyncpg。
- リビジョン作成:
  ```sh
  cd backend && uv run --directory api alembic revision --autogenerate -m "add xxx"
  # 生成物を必ず目視で確認・調整してから commit
  ```
- **expand-contract（N-1 後方互換）必須**（`CLAUDE.md` / issue 072）: ブルーグリーンで旧(blue)・新(green)が**単一 Cloud SQL を同時利用**するため、列追加は nullable/default 付き、削除・改名・NOT NULL 化・型変更は**単一リリースで完結させない**（追加 → 両対応 → blue 退役後の別リリースで縮約）。
- 適用タイミング: **boot では実行しない**。本番は Cloud Run Job `migrate`（`infra/gcp/cloud-run.tf`）をデプロイ内で先行実行、ローカル本番相当は `compose.prod.yml` の `migrate` サービス、dev は起動時リトライループ。

## 4. インフラ構成の変更（Terraform）

- 本体: `infra/gcp/`（`cloud-run.tf` / `load-balancer.tf` / `database.tf` / `cloud-tasks.tf` / `secrets.tf` / `monitoring.tf` / `networking.tf` / `iam.tf` / `cloud-armor.tf` / `storage.tf` / `artifact-registry.tf` / `landing.tf` / `apis.tf` / `variables.tf` / `outputs.tf`）。
- 環境値: `infra/gcp/environments/{stg,prod}.tfvars`（`domain` など）。シークレットは tfvars に置かず **CI から `TF_VAR_*`** で注入。
- ブートストラップ（初回のみ・別スタック）: `infra/bootstrap/gcp/`（WIF プロバイダ・deploy SA・tfstate バケット。deploy SA には `roles/run.admin` 等を付与済み）。
- 変更手順（ローカルで確認する場合）:
  ```sh
  cd infra/gcp && terraform init
  terraform validate
  terraform plan -var-file=environments/stg.tfvars
  ```
  `apply` は通常 CI（デプロイワークフロー）が実行する。手動 apply は state ロックとシークレットに注意。
- 注意: api サービスの `image` / `traffic` は `lifecycle { ignore_changes }` 済み（リビジョン/トラフィックは gcloud 主導、§8）。破壊的な単一 apply は避ける。
- 構成図（`docs/infra/`）は実コード基準。インフラを変えたら図（`*.drawio` / `infrastructure.png`）と `docs/infra/README.md` も更新する。

## 5. CI / CD の変更（`.github/workflows/`）

| ワークフロー | トリガー | 役割 |
|---|---|---|
| `ci.yml` | push / PR（`develop`,`main`） | lint・型・テスト（backend/frontend） |
| `deploy-stg.yml` | **手動（`workflow_dispatch`）** | staging デプロイ（コスト削減のため自動 push 停止中） |
| `deploy-prod.yml` | タグ `v*.*.*` push（**承認必須**） | production デプロイ |
| `deploy-gcp.yml` | 上記から `workflow_call` | イメージ build/push → Trivy → **migrate Job → 段階カナリア → apply**（§8） |
| `release.yml` | タグ `v*.*.*` push | CHANGELOG 見出しのリント + GitHub Release 作成 |
| `pr-review.yml` | PR | Gemini による自動コードレビュー |
| `zap.yml` | 手動 | OWASP ZAP スキャン |

変更時の注意:
- 認証は **WIF のみ**（長期鍵なし）。`vars.GCP_WIF_PROVIDER` / `vars.GCP_DEPLOY_SA` は bootstrap 出力。
- 秘密は GitHub Secrets → `TF_VAR_*` にマップ（`deploy-gcp.yml` 参照）。ワークフローに平文で置かない。
- deploy 系は `concurrency` で環境ごとに直列化。編集後は対象ブランチへ push した版が実行される点に注意。
- ⚠ `release.yml` は `scripts/extract-changelog.sh` を参照するが**現状リポジトリに存在しない**。タグ運用の前に同スクリプト（`## [X.Y.Z]` セクション抽出）を用意するか、workflow を調整すること。

## 6. デプロイ作業

- **staging**（手動）:
  ```sh
  gh workflow run deploy-stg.yml --ref develop
  # または GitHub UI: Actions → Deploy Staging → Run workflow
  ```
- **production**（タグ）: `v*.*.*` タグの push で `deploy-prod.yml`（承認）+ `release.yml` が発火。
- デプロイ内部フロー（`deploy-gcp.yml`、issue 072）:
  1. api / service イメージを build & push（Trivy で CRITICAL/HIGH をブロック）
  2. `terraform apply -target=google_cloud_run_v2_job.migrate` → `gcloud run jobs execute <migrate> --wait`（**expand マイグレーションを先行適用**）
  3. api を `--no-traffic --tag green` でデプロイ → `green=10` → LB 経由ヘルス確認 → `green=100`（**段階カナリア**、旧リビジョン保持）
  4. `terraform apply`（full）で worker・LB・監視を収れん
- **ロールバック**: 旧リビジョンへ即時切替。
  ```sh
  gcloud run services update-traffic <api-service> --region <region> --to-revisions <OLD_REVISION>=100
  ```
- 前提: `deploy-stg`/`prod` の tfvars に `domain` 設定済み（未設定だと LB フロントが作られず到達不可）。初回のまっさらな環境では api サービスの初回作成が別途必要。

## 7. リリース手順

`/release-version` スキル（`.claude/skills/release-version/SKILL.md`）に従う。要点:

1. バージョン決定（`0.0.x`=プレリリース、`0.1.0+`=正式）。
2. 前タグからの変更を収集し `CHANGELOG.md`（日本語・である調）を更新。見出しは厳密に **`## [X.Y.Z] - YYYY-MM-DD`**（`release.yml` がリント）。箇条書きは絵文字なし・要点をインライン太字・PR/issue は可能な範囲で参照。
3. バージョンバンプ: `backend/pyproject.toml` / `frontend/package.json`。
4. ロック更新: `cd backend && uv lock` / `cd frontend && bun install`。
5. ドキュメント再生成（§10）: OpenAPI・ER 図。ユーザー向け変更があれば取扱説明書も更新。
6. 検証後にタグ push → `deploy-prod` + `release.yml`。**コミット/タグのタイミングはユーザーが判断**（スキルは自動 push しない）。

## 8. ドキュメント更新作業

- **API リファレンス**（`docs/reference/openapi.json`）:
  ```sh
  cd backend && uv run --directory api python -m app.scripts.export_openapi
  ```
- **DB ER 図**（`docs/reference/schema.dbml`、dbdiagram.io で可視化）:
  ```sh
  cd backend && uv run --directory api python -m app.scripts.export_dbml
  ```
  どちらもルート定義 / `SQLModel.metadata` から純粋生成（DB 不要）。ルート・スキーマ・モデルを変えたら再生成。
- **取扱説明書**（`docs/取扱説明書/README.md` + スクショ）: 画面が変わったら §「スクショ再取得」。
  ```sh
  # 前提: デモモードで起動 + seed_demo + bun run dev（frontend/screenshots/README.md 参照）
  cd frontend && bun run screenshots     # docs/取扱説明書/images/ と manifest を更新
  ```
  本文はドラフト/実装に合わせて手動（またはエージェント支援）で更新。サブ見出しは読み順の通し番号。
- **インフラ図**（`docs/infra/`）: Terraform / 実コードを変えたら図と README を更新。
- **設計・課題**（`docs/issue/NNN-*.md`）: 大きめの変更は issue ドキュメント化（`/issue` スキルで GitHub issue も作成可）。
- **本運用手順書**（このファイル）: 手順・ワークフロー・スキルを変えたら更新。

## 10. トラブルシュート / 可観測性

- ローカルログ: `scripts/save-container-logs.sh` / `scripts/dev-up.sh`（`docs/logs/` に保存）。
- 本番: 構造化 JSON ログ（Cloud Logging、`X-Request-ID` / trace 相関、issue 302）。5xx ログメトリック + アラート、`/api/v1/health`（liveness）・`/api/v1/health/ready`（readiness=DB 疎通）。
- 解析が固まる/失敗する系は `service` のログと `jobs` テーブル（`status`/`progress`/`result_data`）を確認。
- デプロイ失敗時はカナリアのヘルスゲートで旧リビジョンへ自動復帰（§6 ロールバック）。
